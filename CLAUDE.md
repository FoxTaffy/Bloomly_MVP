# Bloomly — правила для Claude

Стек: Vue 3 + Tailwind 4 (frontend), Fastify + Prisma + PostgreSQL (backend), Expo (mobile), docker compose.
Язык общения и текстов интерфейса — русский (есть i18n, не хардкодить строки там, где уже используется перевод).

## Фронтенд: стили (DRY, самое важное)

Единый источник дизайна — `frontend/src/assets/style.css` (`@theme` с токенами `brand-*` + `@utility`).
Дополнительно: `assets/transitions.css` (переходы), `assets/post-media.css` (медиа поста).

Бренд (цвета, шрифт Nunito, кнопки, поля, лого, иконки): `docs/brand-guide.md`. Цвета вне палитры гайда не вводить.

Порядок действий для любой верстки:
1. **Сначала найти готовое.** Утилиты: `card-surface`, `panel-card`, `popover-panel`, `menu-item`, `feed-tab`,
   `toolbar-btn`, `icon-btn`, `icon-btn-primary`, `field-input`, `field-label`, `floating-pill`, `skeleton`,
   `pill` / `pill-idle` / `pill-active` / `pill-tint`, `chip`, `section-title`, `modal-form`. Перед созданием
   чего-то нового выполнить `grep -n "@utility" frontend/src/assets/style.css` и посмотреть 2–3 похожих компонента.
2. **Править общее, а не копировать.** Нужно изменить рамку, радиус или отступ на 1 px — меняется утилита в
   style.css, и это затрагивает все места сразу. Не добавлять локальное переопределение в одном компоненте.
3. **Новый повторяющийся блок** (встречается 2+ раза) → `@utility` в style.css, а не цепочка
   `bg-brand-card border … rounded-3xl` в каждом файле.
4. **Запрещено:** `<style scoped>` для карточек и контейнеров, хардкод цветов (`#1f223c`, `rgb(...)`) вместо
   токенов `brand-*`, произвольные значения `[13px]` там, где есть шкала Tailwind, новые анимации вне transitions.css.
5. Состояния через `data-active` / `aria-selected`, а не через набор условных классов.
6. Модальные окна — оболочка из `CreateGroupModal.vue` (`bg-black/60 backdrop-blur-xs`, карточка
   `bg-brand-card border-brand-border rounded-3xl`, кнопка закрытия `w-8 h-8 rounded-xl`, заголовок
   `text-xl font-extrabold`). Не придумывать свой вид модалки.
7. Повторяющуюся логику выносить в `composables/` и `lib/`, а не копировать между компонентами.

Если без нового стиля не обойтись, в ответе сказать об этом одной строкой: что добавлено и почему
подходящей утилиты не нашлось.

## Shop и Dealers' Den — разные вещи

- Стикеры и рамки аватара живут **только в Shop**. В DD их нет (ни вкладок, ни лотов, ни валидации).
- Новые функции магазина не заводить через `DealerListing`.
- Не переносить функции из одного раздела в другой без прямой просьбы.

## Деньги

- Счета заказов (`payment_request` с `orderId`) — реальные платежи из кошелька BLM в escrow
  (`Order.escrow_*`), владельцу группы уходят после `confirm-completion`. 1 BLM = 1 $.
- Обычные платёжные запросы в чате (без `orderId`) — просто отметка «оплачено», движения денег нет.
  Не добавлять движение денег без согласования.

## Проверки

- Фронтенд: `bash scripts/check-frontend.sh` (vue-tsc + vite build в контейнере).
- Бэкенд: `bash scripts/check-backend.sh` (tsc), тесты — `bash scripts/test-backend.sh [файлы]`.
- **Baseline:** на чистом HEAD падают 24 бэкенд-теста (payments.test.ts ×16 — ждут курс 90, а контейнер берёт
  живой курс ЦБ; dealers-den-raffle ×4, dealers-den-visibility ×1, feed-author-privacy ×1,
  security-content-access ×1, verification-groups ×1). Сравнивать с этим списком, прежде чем винить свою правку.
- Не говорить «готово» без вывода сборки или тестов. Если что-то не запускалось — сказать об этом прямо.
- Визуальные правки проверять в запущенном приложении, а не только по коду.

## Деплой и git

- Код запечён в образы: `docker compose build api frontend && docker compose up -d api frontend`.
  Образы собираются из всей рабочей папки, включая незакоммиченное.
- Миграции Prisma применяются сами при старте `api`. Статус: `docker compose exec -T api npx prisma migrate status`.
  С хоста `DATABASE_URL` не резолвится (хост `db` только в docker).
- `git push` с этой машины падает (нет учётных данных GitHub) — коммитить локально, пушит пользователь.
- В рабочем дереве много чужих незакоммиченных правок: коммитить только свои файлы через `git add <пути>`,
  без `git add -A`. Одна задача — один коммит.

## Версии (semver)

Каждое изменение логики или интерфейса, которое попадает в коммит, поднимает версию. Её видно в шапке сайта
рядом с лого («бета X.Y.Z», берётся из `frontend/package.json`); версия API — `backend/package.json`.

- Вручную версию **не править**: её поднимает хук `.githooks/pre-commit` (`scripts/agents/version-bump.mjs`),
  отсчитывая от версии в HEAD. Если коммит затрагивает `backend/`, поднимается и версия API.
- Уровень: `fix:`, `refactor:`, `docs:` → patch (по умолчанию); `feat:` → `BUMP=minor git commit …`;
  несовместимые или крупные релизы → `BUMP=major`.
- Не создавать мелкие коммиты ради коммитов: один коммит = одна завершённая правка = один подъём версии.
- `SKIP_AGENTS=1` отключает и сканер секретов, поэтому без прямой просьбы пользователя им не пользоваться.
- Перед деплоем проверить, что версия в шапке соответствует `package.json` после сборки.

## Как работать

- Перед новой функцией искать аналог в кодовой базе и следовать его структуре. Backend-модули лежат в
  `backend/src/modules/<имя>/` (routes → controller → service), фронтенд — `views/` + `components/` + `composables/`.
- Не расширять задачу: заметил соседнюю проблему — сообщить, не чинить молча.
- Сообщения коммитов — на русском в стиле истории (`feat(shop): …`, `fix: …`).
